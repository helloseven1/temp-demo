一个人带着Cloud Code、Codex或Cursor智能体,怎么从0到1完整地交付一个Web和App项目呢，假设今天真的接到一个项目，产品、交互和UI都已经确认，现在只差开发，一个人到底要怎么指挥这些工具，才能把Web和App从空目录做到可以交付呢，
这些工具的工作方式大体相通，今天我们就以Cloud Code为例，后面的操作全部直接用Cloud Code来讲，我们不讲抽象方法，直接拿一个叫PaperTree的模拟交易项目来拆完整电路，如果你也想照着这套流程，带着智能体完整做一遍项目，可以先点个关注，再把这期收藏下来，后面搭到哪一步，就回来对照哪一步，身边要是也有人，正在用AI做开发，可以把这期转发给他，
好，准备好以后，我们现在就正式进入PaperTrade项目。我们假设这个项目一共有六个页面，分别是，登录，行，自选，股票详情，下单确认，持仓。用户登录以后，可以搜索股票，进入详情，以指定价格，提交模拟买单，再到持仓页，查看数量，成本，和剩余余额，Web和App的业务相同，但Web使用左侧导航，App使用底部导航，
后端接口还在开发,所以两个前端先连接同一套模拟接口,等真实接口上线以后再替换地址。真正开始之前,先把项目文件夹搭出来。根目录叫PaperTrade,里面先建立Docs、Design和ROS三个文件夹。Docs专门放产品文档和开发说明。Design专门放Web与App的设计稿。ROS专门放两个端都必须遵守的业务规则和验收样例,然后把现有资料放进去。
这份文件写每个请求需要什么参数又会返回什么数据。设计稿则分别放进DesignWeb和DesignApp。
资料准备好以后，整条交付链路可以拆成11步，而且每一步都先创建对应文件，再让Cloud Code按文件执行。如果是你接到这个项目，你会先初始化工程，还是先把需求和规则整理清楚呢，你可以先在心里留一个答案，等整条链路走完以后，再看看自己的顺序会不会调整，不管你刚才选的是哪一个，在PaperTree的项目里，我们先不碰代码，
第一步，只做需求审查，而且要把审查结果真正落到文件里，先让cloudcode，在docs目录新建RequirementAudit.md。这是一份专门记录需求审查结果和带确认问题的文件。文件里预先建立六个部分，分别用来记录页面清单，页面状态，用户流程，web与app的差异，页面与接口的对应关系，以及带确认问题，文件结构准备好以后，再让cloudcode，阅读prd
交互说明，接口定义，和设计稿，把分析结果填进去，假设这时候PRD和交互稿写的不一样，我们能不能让Cloudcode自己选一个呢，这个是肯定不行的，因为它选出来的是技术答案，不一定是产品真正想要的答案，PaperTrade项目，在这里会发现三个冲突，第一个冲突是，PRD说，下单成功后直接进入持仓页，但交互稿里还有成功弹窗，
第二个冲突是，设计稿里同时出现试价单和限价单，但接口只支持限价单，App的导航已经确定，可Web的导航位置没有说明，这是第三个需要确认的问题，这些问题不能让Cloud Code自己决定，所以负责人要给出明确答案，下单成功后，先显示弹窗，用户点击查看，持仓以后再跳转，当前版本只实现限价单，试价单入口保持禁用，
外部的导航方式也确定下来，统一使用左侧导航，每个答案都写回RequirementAudit.md,并标上D1Session001,D1Session002这样的编号。这样CloudCode后面再次处理相关任务时,会先查这份需求审查记录,不会重新猜一遍。需求里的冲突都确认完以后,接下来才能决定代码怎么组织,所以第二步要创建架构说明文件。在docs目录新建Architecture.md
这份文件专门记录项目使用什么技术，代码放在哪里，以及不同模块之间怎么连接，先在文件里写出最终目录，web工程，放在web，使用next.js，app工程，放在app，使用flutter，模拟接口，放在mockapi，两个端，共同遵守的业务样例，放在rules，统一的颜色，字号，和兼具，放在design tokens，这里你可能会问，web和app，都有按钮、输入框和弹窗，那是不是把所有组件都共享，
附用率就会更高呢，表面上看，确实能省一点代码,对吧，可Next.js和Flutter连底层语言都不同，硬共享只会让两个端互相牵制，接着在Architecture到MD里写清边界，Next.js和Flutter使用的语言不同，所以两个端不直接共享代码，而是共同读取接口定义，业务验收样例，和设计规则，再分别生成TypeScript类型和DAT模型，
Web组件只放在Web,Flutter Widget只放在App,谁也不能为了复用而越过边界。架构文件写完以后,先让Cloud Code检查有没有循环依赖,重复目录,或者说不清归属的代码。如果一个文件以后放在哪里都判断不出来,说明架构还没定清楚。这时不能开始初始化工程。目录和模块边界检查清楚以后,架构算是定下来了。
可架构写在文档里，并不代表Cloud Code后面一定会照着执行。所以第三步，还要创建项目规则文件，在项目根目录新建Cloud MD，这是Cloud Code每次进入项目时，都会先读取的工作规则文件，这些边界，如果只在聊天里提醒一次，等到新绘画，或者新字智能体，开始工作时，它还能不能记得住呢，其实很难，所以我们才要把规则写进Cloud Mid，让它们跟着项目一直存在，
这份文件里，先写全局规则，Web 的TypeScript 必须开启严格模式，Flutter 必须通过静态检查，两个端的页面都不能直接发送网络请求，必须经过各自的请求层，接口模型只能根据docs openapi.yaml生成，不能重复手写，和Flutter 还必须使用Rules目录里的同一组业务样例，同时也不能私自修改已经确认的需求文件，全局规则，写完以后，再补上任务完成规则，
修改Web后,要运行Lint、类型检查和测试。修改Flutter后,要运行格式检查、静态检查和测试。只要有一项检查失败,任务就不能宣布完成。所有检查通过以后,还要提交本次修改的文件,实际执行的命令,退出结果和剩余风险。CloudMD写完以后,相当于先给Cloud Code建立了工作制度。后面无论启动多少个子智能体,都要先让他们读取这份文件,再开始自己的任务。
工作规则固定以后，cloudcode已经知道什么能做，什么不能做，可它还不知道整个项目应该先做哪一块，要把执行顺序也固定下来，第四步，就要建立项目任务板和单任务文件，先在docs目录创建TaxMD，这是整个项目的任务总表，每一行都要有任务编号，任务名称，前置依赖，当前状态，和对应的任务说明文件，
PaperTree的项目可以拆成14个任务。T1负责初始化Web和Flutter。T2负责生成两端的数据模型和请求代码。T3负责建立统一的颜色、字号和间距。DG准备好以后,T4建立登录规则。T5和T6分别完成Web与Flutter登录。
接下来的T7和T8负责行情列表与股票详情。T9建立下单规则，T10和T11分别完成两端的下单页面。最后由T12完成持仓,T13跑通完整流程,T14执行发布验收。看到14个任务以后,那是不是可以一次启动14个子智能体,让它们同时开工呢?这个肯定不行。接口、设计规则和登陆规则都没定下来时,页面做得越快,后面反攻的也就越快。
既然不能一起开工,我们就要把依赖关系写进TASMD。T2和T3必须在页面开发之前完成。T4通过以后,T5和T6才能并行。行情列表和股票详情可以在请求层稳定以后并行。T9会影响订单、余额和持仓。所以两个端的下单页面必须等T9通过以后再开始。执行顺序排出来以后,我们还得解决另一个问题。那就是每个任务具体做到什么程度才算完成。只有一张总表回答不了这个问题。
所以在建立Docs Tasks文件夹,给每个任务单独创建说明文件。比如T5对应Docs,Tasks,T05,Web,Login.md。这份文件里要写任务目标，前置输入，允许修改的目录，禁止修改的文件，具体交付物，验收命令和完成证据。任务范围和依赖关系都排好以后才真正进入执行阶段。
按照任务版的顺序，第五步，先执行T1，初始化整个工程，先创建 docs，tasks，t01，project，setup.md，这份任务文件明确要求Cloudcode，只能建立web，app，mocapi，和基础配置，不能提前写登录，行情或者下单代码，
假设这一步，连web都构建不了，flutter也跑不起来，那我们还要不要先让它把登录页写出来呢，肯定先不要，因为这时候继续写页面，只会把基础问题盖得更深，所以T1的反馈只有两种，通过就继续，失败就留在这一层修复，web使用pnpm安装next.js,typescript,eslint和vitest
App使用Flutter创建工程，在配置静态检查和FlutterTest。模拟接口目录，先建立空服务和启动命令，但这一步不添加业务数据。执行结束后，在Docs Evidence目录创建T1MD，这是一份专门保存T1验收证据的文件。里面记录，Web构建命令，Flutter静态检查命令，两个工程的启动结果，以及有没有依赖冲突，
只有TE、MD里的检查全部通过，TASTE、MD里的TE才能从进行中改成完成，外部，和Flutter都能独立启动以后，项目的外壳已经搭好了，页面还不知道该读取什么数据，为了先把数据通路接起来，第六步，要建立接口生成规则和模拟接口，先创建DocsTasksT02ApiClient.md这份任务文件要求，CloudCode读取DocsOpenAPI.yam
，分别把TypeScript，数据模型生成到Websrc API Generated，把Dart，数据模型生成到Appla BIPI Generated，任务文件里还要规定，两个目录都属于自动生成区域，后面的页面任务，只能调用，不能手工修改。Next.js和Flutter，分别在自己的请求层，处理接口地址，键权，超时，和错误映射，页面只能调用Login，Get Quotes，Create Order，这类业务方法。
不能自己拼请求地址，真实后端还没准备好，那前端是不是只能停下来等呢，其实不用，所以我们在Mock API目录创建Scenarios.json，这份文件专门记录模拟接口要返回的场景，包括登录成功，401，登录失败，行情空列表，下单余额不足，和服务器超时，Cloud Code 根据Scenarios.json，实现模拟接口以后，再创建Docs Evidence TRMD，
记录两端模型生成结果，接口测试结果和每个模拟场景的返回结果，只有这些证据都存在，接口结构才能冻结下来，接口结构冻结以后，页面已经知道怎么请求数据了，但登录能不能提交，下单金额怎么算，这些业务判断还没有统一，如果现在直接做业面，两个端，还是会各写一套，所以第七步，要先建业务规则文件，再做登录和下单，我们先拿登录来做，
假设现在只给cloudcode一句完成登录页,你觉得web和flutter最后会不会写出两套不同的校验呢?这个是很有可能的,所以这里不要直接写页面,而是先在Rules目录创建login cases.json。这份文件就是web和flutter共同遵守的登录规则表。文件里每条规则都要包含编号、输入、预期结果和错误文案。
比如Login001 写邮箱格式错误时不允许提交。Login002 写密码少于8位时不允许提交。Login003 写接口返回。401 时显示账号或密码错误。Login004 写请求进行中不能重复点击登录。规则文件确认以后,在创建 docs,tasks,t04,login,ruth.md
使用FlutterTest读取同一份文件，两个端先跑出失败结果，再分别补齐校验代码，直到所有登录样例都通过，下单也用同样的方法，先创建RulesOtherCases.json，这份文件，写清买入数量必须是100的整数倍，价格最多两位小数，预计金额不能超过可用余额，提交失败，不能提前扣钱，提交成功以后才能更新持仓，
金额规则还要明确写成，以分为单位的整数计算，因为直接用小数计算，188.50美元乘以100股，后续累加可能出现精度误差，规则确认以后，再创建docs,tasks,t09,order,ruth.md,让next.js和flutter分别读取同一组下单样例,完成测试和实现。这样两个端虽然不共享代码,但执行的是同一套业务标准。
登录和下单的业务标准都固定以后，页面开发终于可以开始了，可不同页面会修改不同工程，有些能够同时做，有些必须等待钳制结果，所以第八步，要先为页面建立独立任务文件，再安排并行。外部，登录对应Docs,Tasks,T05web,Login,Mod,
这份文件写明，只能修改Web，必须读取RequirementAudit.md,LoginCases.json和Web登录设计稿，交付桌面布局，窄屏布局，输入错误，请求加载和登录失败五种状态。Flutter登录对应Docs Tasks T06,Flutter,Login,MD。这份文件写明，只能修改App，必须读取同一份需求审查记录和登录规则，
还要额外处理软件盘，输入框聚焦，安全区域和系统返回。Web和Flutter的登录任务文件都准备好以后,还不能看到两个任务就直接并行。那我们又该怎么判断它们能不能同时做呢?其实就看它们会不会修改同一批文件,以及其中一个是否依赖另一个的结果。
按照这个标准再来看，Web登陆和Flutter登陆都只读取公共规则，又分别修改不同工程，所以这两个任务确实可以并行。这时才让Cloudcode启动两个字智能体。并行期间，存放需求和开发说明的Docs，存放业务样例的Ruth，以及存放颜色，字号和兼具的Design Tokens全部保持只读。一个字智能体只能修改Web工程，另一个只能修改Flutter工程，这样它们就不会争抢公共文件。
行情列表，股票详情，和下单页面也按照同样的方法处理。先创建各自的任务文件，写清输入，范围和验收条件，再根据TaskMD里的依赖关系，决定串行还是并行，页面任务安排出去以后，我们不能只等Cloudcode回忆句完成了，还得建立一套能回收结果的反馈机制，所以，第九步，要给每个任务建立验收证据文件，先在Docs，Evidence，目录为当前任务创建同名文件，
比如Web 登录完成后，证据写进 Docs Evidence T5-MD。Flutter 登录完成后，证据写进 Docs Evidence T6-MD。每分证据都分三部分。第一部分，记录代码检查，包括Lint，类型检查和单元测试。第二部分，记录行为检查，包括按钮禁用，错误提示，面跳转和接口失败。
第三部分，记录视觉检查，包括截图地址，设计稿地址，和还存在的差异。测试全部变率以后，是不是就可以把任务关掉了呢，这个时候还不行，因为测试能证明逻辑符合预期，却不能证明页面真的好用，也不能证明画面和设计稿一致，Web登录要用Playwright分别截取1440像素和390像素的页面，Flutter登录要在模拟器里检查键盘弹起，加载状态和登录失败，
如果测试都通过，但Web按钮宽度和设计稿不一致，或者Flutter键盘挡住按钮，证据文件就必须写未通过，对应任务也不能关闭，每个页面都拿到自己的验收证据以后，单任务开发算是完成了，接下来要看的，就不再是某一个页面，而是用户能不能把所有页面连续走一遍，到了这里，登陆，行情，详情，和下单页面都已经各自通过验收，那这个项目是不是就完成了呢，
其实还没有，因为单个页面能打开，不代表用户从登陆走到持仓的整条路真的能走通，所以第十步，要先创建完整流程文件，再跑跨页面集成，在Ruth目录创建Tradflow到Jason，这份文件专门记录最终要跑通的用户路径，里面写轻测试账号登陆，搜索AAPL，进入股票详情，以188.50美元买入100股，
看到成功弹窗，点击查看持仓，再检查持仓数量，成本和剩余余额，接着创建DocsTasksT13integration.md这份任务文件要求Web和Flutter都严格执行tradeflow.json不能各自换一条更容易通过的流程。Web根据这份流程生成playwrite测试,Flutter根据同一份流程生成integration test。比如Flutter下单成功以后，
错误地回到了航行首页，就要修复成功弹窗的路由目标，再从登陆开始重跑，不能只手动打开持仓页，证明页面存在，两个端都通过以后，把完整命令，运行结果，失败修复记录，和最终截图，写进Docs Evidence T13MD，这才算完成跨页面集成，Web和Flutter都跑通同一条用户路径以后，功能层面的集成已经完成，
最后还要把这些结果一条条对应回最初的产品需求。所以第十一步要建立最终交付验收表。在Docs目录创建ACCEP10-MD,这是项目交付前使用的需求验收表。先把PRD里的每条需求编号列出来。再为每一条补上Web实现位置，Flutter实现位置，对应测试和证据文件。然后让Cloud Code执行最后一轮检查。Web要通过Lint、类型检查，单元测试，构建和完整流程，
Flutter 要通过格式检查，静态检查，单元测试和集成测试，整个项目还要检查临时日志，硬编码密钥，被跳过的测试和超出需求的功能，最后交付的内容不止Next.js 的外部和Flutter App，还包括Docs里的需求审查，架构说明，任务总表和验收表，Rules里的登录，下单和完整流程规则，Moke RP里的模拟接口，以及Evidence里的全部完成证据，
等需求、代码、测试和证据都在验收表里对应起来。PaperTree的项目才算真正走道交付。这就是一个人指挥CloudCode,完成整个项目的完整链路。每一步都不是先让CloudCode自由发挥,再想办法检查结果。而是先创建一个文件,把目标、范围、规则和验收方式固定下来,然后才允许它执行。CloudCode负责写代码。
规则文件负责统一标准，任务文件负责限制范围，证据文件负责证明结果，而你负责决定什么时候可以进入下一步，把这套链路建立起来以后，一个人才真正有可能带着Cloud Code和他的子智能体，把一个项目稳定地交付出来，你们平时用智能体做项目时，最容易跳过的，到底是需求审查，任务拆解，还是最后的验收证据呢，
